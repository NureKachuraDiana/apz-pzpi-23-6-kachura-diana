3.1 Мета заняття

Розробити вебзастосунок системи екологічного моніторингу EcoMonitor з використанням фреймворку Next.js, забезпечити взаємодію клієнтської частини із сервером через REST API та реалізувати функціонал моніторингу, аналізу й перегляду екологічних показників у режимі реального часу.

3.2 Постановка задачi

У межах лабораторної роботи необхідно було:
− розробити вебзастосунок для системи EcoMonitor;
− реалізувати взаємодію клієнтської частини із backend-сервером через REST API;
− забезпечити авторизацію та автентифікацію користувачів;
− реалізувати отримання та відображення екологічних даних із сенсорних станцій;
− створити інтерфейс для перегляду екологічних показників, статистики та інтерактивної карти;
− реалізувати систему ролей та контроль доступу користувачів;
− організувати структуру проєкту відповідно до сучасних принципів веброзробки;
− спроєктувати UML-діаграми, що описують архітектуру та логіку роботи системи;
− завантажити вихідний код проєкту до GitHub.

3.3 Короткий опис системи

Програмна система EcoMonitor призначена для автоматизованого моніторингу екологічного стану навколишнього середовища з використанням IoT-пристроїв та вебтехнологій. Система забезпечує збір, передачу, збереження, обробку та візуалізацію екологічних даних у режимі реального часу.
Джерелом даних виступають сенсорні станції, які передають інформацію про температуру повітря, рівень вологості, концентрацію CO₂, рівень забруднення повітря, освітленість та інші показники.
Отримані дані надходять на сервер через REST API, де проходять обробку, перевірку та зберігаються у базі даних для подальшого аналізу. Користувачі взаємодіють із системою через вебзастосунок, який надає можливість перегляду інформації у вигляді графіків, статистики, таблиць та інтерактивної карти.
Система підтримує багаторівневу модель доступу користувачів, механізми авторизації та автентифікації, а також інтеграцію із зовнішніми сервісами. EcoMonitor може використовуватись для локального або масштабованого екологічного моніторингу з можливістю подальшого розширення функціональності.

3.4 Розробка Web застосунку
3.4.1 Використанi технологiї

Під час розробки вебзастосунку були використані такі технології:
− Next.js — основний фреймворк для розробки вебзастосунку;
− TypeScript — мова програмування для розробки клієнтської частини;
− Tailwind CSS — бібліотека для стилізації інтерфейсу;
− Axios — бібліотека для роботи з REST API;
− React Context API — для глобального управління станом застосунку;
− REST API — для взаємодії із серверною частиною системи;
− Git та GitHub — для контролю версій;
− Google Maps API — для відображення інтерактивної карти станцій моніторингу.

3.4.2 Архiтектура Web застосунку

Вебзастосунок побудований відповідно до модульного підходу та сучасних принципів frontend-розробки. Архітектура системи забезпечує масштабованість, повторне використання компонентів та зручність підтримки програмного коду.
Структура проєкту включає такі основні модулі:
1. app:
Містить сторінки застосунку, маршрутизацію та основну структуру інтерфейсу користувача.
2. api:
Містить модулі для взаємодії із серверною частиною системи через REST API.
3. components:
Містить повторно використовувані компоненти інтерфейсу користувача.
4. сontexts
Містить глобальні контексти застосунку для управління авторизацією, станом користувача та іншими даними.
5. utils
Містить допоміжні функції та утиліти для обробки даних.
6. i18n
Містить конфігурацію локалізації та мовні ресурси застосунку.
Для реалізації системи доступу використовується механізм ролей користувачів. Відображення функціоналу здійснюється динамічно через навігаційне меню залежно від ролі користувача, а контроль доступу додатково забезпечується серверною частиною системи.

3.4.3 UML-діаграма прецедентів (Use Case Diagram)

Для опису функціональних можливостей вебзастосунку EcoMonitor та взаємодії користувачів із системою була побудована UML-діаграма прецедентів. Дана діаграма демонструє основні сценарії використання системи, ролі користувачів та доступний для них функціонал.
Use Case Diagram дозволяє представити систему з точки зору кінцевого користувача та показує, які дії можуть виконуватись різними категоріями користувачів у межах вебзастосунку EcoMonitor. Діаграма також відображає залежності між окремими прецедентами та демонструє структуру доступу до функціональних можливостей системи.
У системі визначено три основні ролі користувачів:
− адміністратор (Admin);
− оператор (Operator);
− спостерігач (Observer).
Користувач із роллю «Admin» має найширший рівень доступу до функціоналу системи. Адміністратор може виконувати моніторинг системи, керування користувачами, перегляд статистики станцій, роботу з шаблонами сповіщень, резервне копіювання даних, а також планування технічного обслуговування моніторингових станцій. Крім цього, адміністратор має доступ до управління сенсорами та створення нових сенсорів у системі.
 
Рисунок 3.1 – UML-діаграма прецедентів вебзастосунку EcoMonitor

Роль «Operator» призначена для роботи з моніторинговими станціями та оперативного контролю екологічних показників. Оператор може переглядати інформацію про станції, працювати із сенсорами, виконувати підтвердження критичних сповіщень, експортувати дані та брати участь у процесах технічного обслуговування системи.
Роль «Observer» має обмежений рівень доступу та використовується переважно для перегляду інформації. Користувачі цієї ролі можуть авторизуватись у системі, переглядати станції на карті, отримувати інформацію про сповіщення, переглядати профіль користувача та змінювати персональні налаштування. Також для спостерігачів передбачена можливість створення нового облікового запису в системі.
На діаграмі також відображені залежності типу include між окремими прецедентами. Наприклад, перегляд статистики станцій включає перегляд станцій на карті, а функції редагування профілю користувача та налаштування мови, теми й сповіщень пов’язані з модулем профілю та налаштувань. Управління користувачами включає перегляд списку користувачів системи, а створення сенсорів пов’язане із загальним модулем роботи із сенсорами.

3.4.4 UML-діаграма компонентів (Component Diagram)

Для опису архітектури вебзастосунку EcoMonitor була побудована UML-діаграма компонентів, яка демонструє структуру системи, основні програмні модулі та взаємозв’язки між ними. Дана діаграма дозволяє відобразити організацію клієнтської частини застосунку, розподіл функціональності між компонентами та способи їх взаємодії із серверною частиною системи й зовнішніми сервісами.
Вебзастосунок побудований за модульною архітектурою з використанням фреймворку Next.js та App Router. Такий підхід забезпечує чітке розділення відповідальності між інтерфейсом користувача, глобальним станом застосунку, API-шаром та допоміжними модулями. Архітектура сприяє масштабованості проєкту, спрощує підтримку коду та дозволяє ефективно розширювати функціональність системи.
Основою системи є клієнтський інтерфейс, який включає сторінки застосунку, компоненти інтерфейсу та систему навігації. До складу інтерфейсного шару входять сторінки авторизації, реєстрації, перегляду станцій моніторингу, перегляду показників сенсорів, статистики, налаштувань користувача та адміністративної панелі. Навігація між сторінками реалізована за допомогою App Router у Next.js.

 
Рисунок 3.2 – UML-діаграма компонентів вебзастосунку EcoMonitor

Окрему роль у структурі застосунку відіграють повторно використовувані UI-компоненти, розміщені у модулі components. До них належать форми авторизації, елементи навігації, компоненти відображення станцій, карти, таблиці, графіки та інші елементи інтерфейсу. Для стилізації інтерфейсу використовується Tailwind CSS та бібліотека компонентів shadcn/ui.
Для забезпечення глобального управління станом застосунку використовуються React Context-компоненти. Компонент AuthContext відповідає за збереження інформації про поточну сесію користувача, його роль та авторизацію у системі. LanguageContext та ThemeProvider забезпечують підтримку локалізації й перемикання тем оформлення інтерфейсу. Додатково використовуються hooks та допоміжні сервіси для роботи зі сповіщеннями та локальним станом інтерфейсу.
Мережевий рівень системи представлений компонентами ApiService та AxiosInstance. ApiService містить типізовані методи для роботи з REST API серверної частини EcoMonitor та забезпечує централізовану взаємодію з backend-сервером. AxiosInstance використовується для надсилання HTTP-запитів, обробки інтерцепторів, роботи із cookies та підтримки механізмів авторизації.
Окремим компонентом системи є модуль типів та DTO-моделей, який використовується для опису структури даних, отриманих із сервера. Це дозволяє забезпечити типізацію даних та підвищити надійність взаємодії між компонентами застосунку.
На діаграмі також представлені зовнішні компоненти системи. REST API EcoMonitor забезпечує обробку запитів вебзастосунку та взаємодію із серверною логікою і базою даних. Для відображення станцій екологічного моніторингу використовується Google Maps JavaScript API. Браузер користувача забезпечує збереження cookies сесії та підтримку механізмів авторизації. Для локального збереження налаштувань, теми оформлення та параметрів локалізації використовується localStorage.


3.4.5 UML-діаграма пакетів (Package Diagram)

Для представлення структури програмного коду вебзастосунку EcoMonitor була побудована UML-діаграма пакетів. Дана діаграма демонструє логічну організацію модулів системи, взаємозв’язки між пакетами та розподіл функціональності між окремими частинами вебклієнта.
Використання пакетної структури дозволяє організувати код відповідно до принципів модульності та сучасної frontend-архітектури. Такий підхід спрощує підтримку проєкту, покращує читабельність коду та забезпечує можливість подальшого масштабування системи.
 
Рисунок 3.3 – UML-діаграма пакетів вебзастосунку EcoMonitor

Центральним елементом діаграми є пакет «app», який містить сторінки вебзастосунку та основну логіку маршрутизації. Саме через цей пакет реалізується взаємодія користувача із системою, відображення сторінок та координація роботи інших модулів застосунку.
Пакет «components» містить повторно використовувані компоненти користувацького інтерфейсу. До нього входять елементи навігації, форми авторизації, компоненти відображення моніторингових станцій, карти, таблиці, модальні вікна та інші UI-компоненти. Даний пакет використовує локалізаційні ресурси та допоміжні бібліотеки для побудови інтерфейсу.
Пакет «contexts» реалізує глобальне управління станом застосунку. У ньому містяться контексти авторизації користувача, локалізації, теми оформлення та інших глобальних параметрів системи. Завдяки цьому забезпечується централізоване управління даними та станом інтерфейсу.
Пакет «api» відповідає за взаємодію вебзастосунку із серверною частиною системи через REST API. У ньому реалізовані модулі для виконання HTTP-запитів, обробки відповідей сервера, роботи з cookies та підтримки механізмів авторизації.
Пакет «hooks» містить користувацькі React hooks, які використовуються для повторного використання логіки в різних компонентах застосунку. До них належать hooks для роботи зі станом, повідомленнями, API-запитами та іншими службовими механізмами.
Пакет «i18n» включає конфігурацію локалізації та мовні ресурси застосунку. Завдяки цьому пакету забезпечується підтримка багатомовності та можливість перемикання мов інтерфейсу користувача.
Пакет «lib» містить допоміжні функції, утиліти та службові модулі, які використовуються в різних частинах системи. До нього входять функції форматування даних, допоміжні сервіси та загальні інструменти для роботи застосунку.
Залежності між пакетами демонструють напрямки використання функціональності між окремими модулями системи. Центральний пакет «app» використовує компоненти інтерфейсу, глобальні контексти, hooks та API-шар. Пакет «components» взаємодіє з локалізаційними ресурсами та допоміжними бібліотеками, а пакет «contexts» використовує модулі локалізації для підтримки багатомовності.

3.4.6 UML-діаграма взаємодії (Interaction Overview Diagram)

Для демонстрації процесу взаємодії між користувачем, вебзастосунком та серверною частиною системи була побудована UML-діаграма взаємодії. Дана діаграма відображає послідовність виконання основних дій під час роботи вебклієнта EcoMonitor та дозволяє проаналізувати процес обміну даними між компонентами системи.
На діаграмі представлений сценарій перегляду моніторингових станцій на інтерактивній карті. Даний сценарій є одним із ключових функціональних процесів вебзастосунку, оскільки забезпечує користувачу можливість отримання актуальної інформації про стан навколишнього середовища та розташування сенсорних станцій.
 
Рисунок 3.4 – UML-діаграма взаємодії вебзастосунку EcoMonitor

Процес взаємодії починається з відкриття користувачем сторінки «Станції / Карта» у вебзастосунку. Після завантаження сторінки клієнтська частина, реалізована на основі Next.js, виконує HTTP-запит до серверної частини системи для отримання списку моніторингових станцій.
Серверна частина системи обробляє отриманий REST-запит та виконує звернення до бази даних для отримання інформації про станції моніторингу та їхні екологічні показники. Після зчитування необхідних даних база даних повертає результати серверу для подальшої обробки.
Після отримання результатів сервер формує відповідь у форматі JSON та надсилає її вебклієнту через REST API. Клієнтська частина застосунку виконує обробку отриманих даних та відображає моніторингові станції на інтерактивній карті у вигляді маркерів.
У процесі взаємодії беруть участь основні компоненти системи: користувач, вебклієнт EcoMonitor, серверна частина та база даних. Діаграма демонструє послідовність обміну даними між компонентами та відображає логіку виконання одного з основних сценаріїв роботи системи.

3.4.7 UML-діаграма діяльності (Activity Diagram)

Для опису логіки роботи системи критичних сповіщень у вебзастосунку EcoMonitor була побудована UML-діаграма діяльності. Дана діаграма демонструє послідовність виконання дій під час перегляду та обробки активних критичних сповіщень, а також відображає взаємодію між вебклієнтом та серверною частиною системи.
На діаграмі представлений процес отримання активних сповіщень для окремої моніторингової станції. Даний сценарій є важливою частиною системи екологічного моніторингу, оскільки дозволяє користувачам оперативно отримувати інформацію про небезпечні або критичні екологічні показники.
Процес починається з відкриття користувачем сторінки станції моніторингу та переходу до вкладки «Сповіщення». Після цього вебклієнт формує HTTP-запит до серверної частини системи для отримання списку активних сповіщень, використовуючи REST API endpoint GET /station-alerts/active.
 
Рисунок 3.5 – UML-діаграма діяльності вебзастосунку EcoMonitor

Серверна частина системи приймає запит, виконує звернення до бази даних та зчитує інформацію про активні сповіщення, пов’язані з відповідною станцією моніторингу. Після обробки даних сервер формує відповідь у форматі JSON та повертає список активних сповіщень вебклієнту.
Після отримання відповіді вебзастосунок виконує обробку даних та відображає список сповіщень користувачу. Якщо серед отриманих повідомлень присутні критичні або високопріоритетні сповіщення, система додатково виділяє їх у користувацькому інтерфейсі для привернення уваги користувача.
Далі система перевіряє можливість підтвердження сповіщення користувачем. Якщо користувач має відповідні права доступу, вебклієнт надсилає PATCH-запит на сервер для підтвердження сповіщення через endpoint /station-alerts/{id}/acknowledge. Серверна частина оновлює інформацію про підтвердження сповіщення, зокрема acknowledgedAt та acknowledgedBy, після чого повертає оновлені дані вебклієнту.
Після отримання оновленої інформації вебзастосунок виконує оновлення списку сповіщень та відображає актуальний стан повідомлень користувачу. Якщо користувач не має прав на підтвердження сповіщень, система працює у режимі лише перегляду.
У випадку відсутності активних критичних сповіщень вебзастосунок відображає відповідне інформаційне повідомлення для користувача.

3.4.8 Локалізація та інтернаціоналізація системи

У вебзастосунку EcoMonitor реалізовано механізм локалізації та інтернаціоналізації інтерфейсу користувача, який забезпечує підтримку декількох мов та можливість їх динамічного перемикання без перезавантаження сторінки. Локалізація реалізована на рівні клієнтської частини застосунку Next.js із використанням React Context та окремого модуля i18n.
Система підтримує українську та англійську мови інтерфейсу. Усі текстові ресурси застосунку організовані у вигляді структурованих словників перекладів, що дозволяє централізовано керувати мовними даними та спрощує подальше розширення мовної підтримки системи.
Для управління поточним станом локалізації використовується глобальний LanguageContext, який надає доступ до поточної мови інтерфейсу, функції її зміни та функції отримання перекладів у будь-якому компоненті вебзастосунку. Такий підхід забезпечує централізоване управління мовними налаштуваннями та дозволяє уникнути дублювання логіки локалізації у різних частинах системи.
Під час ініціалізації вебзастосунку обрана користувачем мова автоматично зчитується з локального сховища браузера localStorage. У разі відсутності збережених параметрів використовується мова за замовчуванням, визначена конфігурацією системи. Це забезпечує збереження мовних налаштувань між сесіями користувача та покращує зручність використання вебзастосунку.
Зміна мови здійснюється динамічно через функцію setLanguage, яка оновлює глобальний стан застосунку та зберігає нове значення у localStorage. Додатково реалізовано синхронізацію атрибуту lang HTML-документа, що забезпечує коректну роботу браузера, пошукових систем та допоміжних засобів доступності.
Для отримання локалізованих текстових ресурсів використовується функція t, яка забезпечує доступ до перекладів відповідно до поточної мови інтерфейсу. Переклади організовані за вкладеною структурою ключів, що дозволяє масштабувати систему локалізації без зміни клієнтської логіки застосунку.
У системі також реалізовано локалізоване відображення дати та часу. Усі часові значення зберігаються на серверній частині у форматі UTC, після чого під час відображення у вебзастосунку автоматично конвертуються у локальний часовий пояс користувача. Такий підхід забезпечує коректне відображення часових даних незалежно від регіону використання системи.
Окремо враховано особливості роботи Next.js та клієнтського рендерингу. Контекст локалізації доступний для всіх дочірніх компонентів застосунку незалежно від етапу їх ініціалізації, що дозволяє уникнути помилок доступу до мовних ресурсів під час початкового рендерингу сторінок.

3.4.9 Взаємодія web-застосунку із серверною частиною

Взаємодія між клієнтською та серверною частинами системи EcoMonitor реалізована відповідно до принципів REST-архітектури з використанням HTTP-запитів та формату обміну даними JSON. Клієнтська частина, розроблена на базі Next.js, взаємодіє із серверною частиною системи, створеною з використанням фреймворку NestJS, через набір REST API endpoint’ів.
Для централізованої роботи з HTTP-запитами у вебзастосунку використовується бібліотека Axios. У системі створено окремий екземпляр AxiosInstance, який містить базові параметри взаємодії із сервером, зокрема адресу API, стандартні HTTP-заголовки, параметри авторизації та механізми обробки помилок.
Базова адреса серверної частини задається через змінні середовища Next.js, що дозволяє гнучко змінювати конфігурацію застосунку залежно від середовища виконання — локальної розробки, тестування або production-середовища — без внесення змін у програмний код.
Для забезпечення коректної роботи авторизації використовується механізм cookies та параметр withCredentials у конфігурації Axios. Це дозволяє автоматично передавати сесійні cookies разом із HTTP-запитами та підтримувати автентифіковану сесію користувача без необхідності повторної передачі облікових даних.
У системі реалізовано централізовану обробку HTTP-запитів та відповідей за допомогою Axios interceptors. Інтерцептори дозволяють виконувати попередню обробку запитів, додавання службових заголовків та централізовану обробку помилок доступу.
У випадку отримання від серверної частини відповіді з кодом 401 Unauthorized вебзастосунок автоматично перенаправляє користувача на сторінку авторизації. Такий механізм забезпечує контроль доступу до захищених сторінок системи та підтримує коректну роботу role-based authorization.
Для передачі даних між клієнтською та серверною частинами використовуються стандартні HTTP-методи GET, POST, PATCH та DELETE. Відповіді сервера обробляються у форматі JSON та використовуються для оновлення стану інтерфейсу користувача у режимі реального часу.
Таким чином, реалізована клієнт-серверна взаємодія забезпечує стабільний обмін даними між вебклієнтом EcoMonitor та серверною частиною системи, підтримує механізми авторизації, обробку помилок та централізоване управління API-запитами.

3.4.10 Налаштування SSL та захищеного з’єднання

Для забезпечення захищеного обміну даними між клієнтською та серверною частинами системи EcoMonitor використовується протокол HTTPS, який забезпечує шифрування мережевого трафіку та захист переданих даних від перехоплення або модифікації.
У межах розробки та тестування вебзастосунку використовуються локальні самопідписані SSL-сертифікати. Генерація сертифікатів виконується за допомогою спеціальних інструментів для створення локальних HTTPS-сертифікатів, що дозволяє забезпечити підтримку захищеного з’єднання без використання зовнішніх центрів сертифікації.
Після генерації SSL-сертифікатів приватний ключ та сертифікат підключаються до серверної частини NestJS під час запуску застосунку. Сервер автоматично використовує HTTPS-з’єднання у випадку наявності відповідних SSL-файлів у конфігурації середовища.
Клієнтська частина Next.js налаштована для роботи із захищеним HTTPS API. Це дозволяє коректно працювати механізмам авторизації на основі cookies, оскільки сучасні браузери обмежують передачу secure-cookie через незахищені HTTP-з’єднання.
У локальному середовищі розробки браузер може відображати попередження щодо довіри до самопідписаного SSL-сертифіката. Така поведінка є стандартною для локальних середовищ тестування та не впливає на працездатність вебзастосунку.
Використання HTTPS також забезпечує коректну роботу сучасних браузерних API та підвищує загальний рівень безпеки системи під час передачі даних між клієнтом і сервером.

3.5 Висновки

У ході виконання лабораторної роботи було розроблено front-end частину програмної системи моніторингу екології EcoMonitor у вигляді сучасного вебзастосунку на базі Next.js. Реалізований вебклієнт забезпечує взаємодію користувачів із системою екологічного моніторингу, підтримує роботу з моніторинговими станціями, сенсорами, критичними сповіщеннями та адміністративним функціоналом.
Під час розробки було реалізовано клієнт-серверну взаємодію із backend-системою на основі REST API, налаштовано механізми авторизації та розмежування доступу відповідно до ролей користувачів. Для забезпечення безпеки передачі даних використано HTTPS-з’єднання та SSL-сертифікати.
У вебзастосунку реалізовано підтримку локалізації та інтернаціоналізації, зокрема підтримку української та англійської мов, механізм динамічного перемикання мови інтерфейсу, а також локалізоване відображення дати та часу.
Під час проєктування системи були використані сучасні підходи frontend-розробки, зокрема компонентна архітектура React, модульна організація структури проєкту, Context API для управління глобальним станом та Tailwind CSS для побудови інтерфейсу користувача.
У межах лабораторної роботи також були побудовані UML-діаграми, які відображають архітектуру, структуру та логіку роботи вебзастосунку EcoMonitor. Зокрема, було створено UML-діаграму прецедентів, UML-діаграму компонентів, UML-діаграму пакетів, UML-діаграму взаємодії та UML-діаграму діяльності.
