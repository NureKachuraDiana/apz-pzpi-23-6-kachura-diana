2.1 Мета  заняття

Розробити мобільний застосунок для системи екологічного моніторингу EcoMonitor на платформі Android з використанням Kotlin, забезпечити взаємодію застосунку із серверною частиною системи та реалізувати функціонал перегляду, аналізу й моніторингу екологічних показників у режимі реального часу.

2.2 Постановка задачi

У межах лабораторної роботи необхідно було:

-розробити мобільний застосунок для Android;
-реалізувати взаємодію мобільного застосунку з backend-сервером через REST API;
-забезпечити авторизацію та автентифікацію користувачів;
-реалізувати отримання та відображення екологічних даних із сенсорних станцій;
-створити інтерфейс для перегляду поточних показників станцiй;
-організувати структуру проєкту відповідно до сучасних принципів Android-розробки;
-спроєктувати UML-діаграми, що описують архітектуру та логiку мобiльного застосунку;
-завантажити вихідний код проєкту до GitHub.

2.3 Короткий опис системи

Програмна система EcoMonitor призначена для автоматизованого моніторингу екологічного стану місцевості з використанням IoT-пристроїв. Система забезпечує збір, передачу, збереження, обробку та візуалізацію екологічних даних у режимі реального часу. Джерелом даних виступають сенсори, що вимірюють основні параметри довкілля, зокрема температуру повітря, рівень вологості, концентрацію шкідливих речовин (CO₂, пил), рівень освітленості та інші показники.
Отримані дані передаються на сервер через REST API, де проходять обробку, перевірку та зберігаються у базі даних для подальшого аналізу. Користувачі взаємодіють із системою через Web та мобільний застосунок, які надають можливість перегляду інформації у вигляді інтерактивних карт, графіків та статистичних показників, а також отримання сповіщень у разі перевищення допустимих норм.
Система підтримує багаторівневу модель доступу користувачів, інтеграцію з зовнішніми сервісами та забезпечує базові механізми безпеки даних. EcoMonitor може бути використана для локального або масштабованого моніторингу екологічної ситуації з можливістю подальшого розширення функціональності.

2.4 Розробка мобiльного застосунку
2.4.1 Використанi технології

Під час розробки мобільного застосунку були використані такі технології:
-Kotlin — основна мова програмування;
-Android SDK;
-Android Jetpack Components;
-Retrofit — для роботи з REST API;
-MVVM-архітектура;
-Git та GitHub — для контролю версій.
-Пiдключення зовнiшнього сервiсу Google Maps for Android SDK.

2.4.2 Архітектура мобільного застосунку

Мобільний застосунок побудований відповідно до архітектурного шаблону MVVM (Model–View–ViewModel).
Архітектура включає такі рівні:

Presentation Layer
Містить Screens, Fragment, ViewModel та UI-компоненти. Відповідає за взаємодію з користувачем та відображення даних.

Domain Layer
Містить бізнес-логіку застосунку, use cases та моделі предметної області.

Data Layer
Відповідає за отримання даних із REST API, локального сховища та їх обробку.

Backend API
Серверна частина системи забезпечує:
-обробку HTTP-запитів;
-автентифікацію;
-доступ до бази даних;
-передачу даних із сенсорних станцій.



2.4.3 UML-діаграма прецедентів (Use Case Diagram)

Для опису функціональних можливостей мобільного застосунку EcoMonitor була побудована UML-діаграма прецедентів. Дана діаграма відображає взаємодію користувачів із системою та демонструє основні сценарії використання мобільного застосунку.
Використовувати мобiльний застосунок можуть два типи користувачiв:
OBSERVER — звичайний користувач, який здійснює перегляд екологічних даних та сповіщень;
OPERATOR — користувач із розширеними можливостями керування станцiями монiторингу та серсорами.
Основним функціоналом мобільного застосунку є перегляд карти моніторингових станцій. Користувач може отримати інформацію про конкретну станцію, переглянути список встановлених датчиків та ознайомитися з останніми показниками екологічних параметрів.
Також у застосунку реалізовано модуль профілю користувача, який дозволяє переглядати та редагувати персональні дані, змінювати тему оформлення, мову інтерфейсу, налаштування сповіщень та систему вимірювання.

 
Рисунок 2.1 - UML діаграма прецедентів (Use Case Diagram)

Окремим функціональним модулем є система сповіщень. Користувачі отримують push-сповіщення при виникненні критичних екологічних показників. У застосунку доступний перегляд списку сповіщень та можливість позначення їх як прочитаних.
Діаграма прецедентів демонструє взаємозв’язки між користувачами та функціональними можливостями системи, а також включення окремих сценаріїв використання через зв’язки <<include>>.

2.4.4 UML-діаграма компонентів (Component Diagram)

Для опису архітектури мобільного застосунку EcoMonitor була побудована UML-діаграма компонентів, яка демонструє структуру системи, основні програмні модулі та взаємозв’язки між ними. Дана діаграма дозволяє на високому рівні показати організацію застосунку, розподіл функціональності між окремими компонентами та способи їх взаємодії.
Мобільний застосунок побудований за багатошаровою архітектурою, що забезпечує чітке розділення відповідальності між інтерфейсом користувача, бізнес-логікою, обробкою даних та мережевою взаємодією. Такий підхід спрощує підтримку проєкту, підвищує масштабованість системи та дозволяє ефективно розширювати функціонал застосунку.
Основою системи є клієнтський інтерфейс, реалізований за допомогою Android Jetpack Compose. До цього шару входять основні екрани мобільного застосунку, серед яких екран авторизації, головний екран із картою станцій, сторінка окремої моніторингової станції, налаштування, профіль користувача та система сповіщень. Навігація між екранами реалізована через MainActivity. Також до інтерфейсного шару входить модуль локалізації, який забезпечує підтримку української та англійської мов.
Інтерфейс користувача взаємодіє із шаром ViewModel, який відповідає за обробку логіки представлення та передачу даних між інтерфейсом і джерелами даних. У цьому шарі реалізовані ViewModel-компоненти для авторизації, роботи зі станціями моніторингу, налаштуваннями, профілем користувача та системою сповіщень. Окремий компонент AlertsViewModel використовується для отримання критичних повідомлень у режимі реального часу через WebSocket-з’єднання.
Наступним рівнем архітектури є шар репозиторіїв, який відповідає за отримання, обробку та передачу даних. Репозиторії виконують роль посередника між ViewModel та мережевим шаром, забезпечуючи централізовану роботу з API та локальними даними. Такий підхід дозволяє ізолювати бізнес-логіку від механізмів отримання інформації.
Мережевий шар забезпечує взаємодію мобільного застосунку із серверною частиною системи EcoMonitor. Для надсилання HTTP-запитів використовується компонент ApiClient та сервіс ApiService. Через REST API мобільний застосунок отримує інформацію про моніторингові станції, показники датчиків, дані профілю користувача та інші системні дані. Для роботи зі сповіщеннями в реальному часі використовується SocketClient та NotificationHelper, які забезпечують взаємодію із сервером Socket.IO.
 
Рисунок 2.2 – UML-діаграма компонентів мобільного застосунку EcoMonitor

На діаграмі також представлені зовнішні компоненти системи. REST API EcoMonitor виконує обробку запитів мобільного застосунку та забезпечує доступ до серверної логіки і бази даних. Socket.IO сервер використовується для передачі push-сповіщень про критичні екологічні показники. Для відображення станцій моніторингу на карті застосунок взаємодіє із сервісом Google Maps. Android Notification Service відповідає за системні push-сповіщення користувача. Локальне збереження налаштувань, параметрів авторизації, мови та теми застосунку реалізовано через SharedPreferences.
Таким чином, UML-діаграма компонентів відображає загальну структуру мобільного застосунку EcoMonitor, демонструє організацію його архітектури та показує взаємодію між внутрішніми компонентами системи й зовнішніми сервісами.

2.4.5 UML-діаграма пакетів (Package Diagram)

Для представлення структури програмного коду мобільного застосунку EcoMonitor була побудована UML-діаграма пакетів. Дана діаграма демонструє логічну організацію програмних модулів застосунку, взаємозв’язки між пакетами та розподіл функціональності між окремими частинами системи.
Використання пакетної структури дозволяє організувати код застосунку відповідно до принципів модульності та багатошарової архітектури. Це спрощує підтримку проєкту, підвищує читабельність коду та забезпечує можливість подальшого розширення функціоналу системи.
Центральним елементом діаграми є пакет «Додаток», який об’єднує основну логіку мобільного застосунку та взаємодіє з іншими пакетами системи. Саме через нього виконується координація роботи інтерфейсу користувача, мережевих компонентів, моделей даних та допоміжних модулів.
Пакет «Екрани» містить компоненти користувацького інтерфейсу, реалізовані за допомогою Android Jetpack Compose. До нього входять екрани авторизації, перегляду моніторингових станцій, налаштувань, профілю користувача та сповіщень. Даний пакет використовує ресурси застосунку для відображення текстів, стилів та графічних елементів.
Пакет «ViewModels» реалізує логіку представлення та забезпечує взаємодію між інтерфейсом користувача й бізнес-логікою застосунку. Через цей пакет здійснюється обробка даних, отриманих із серверної частини системи, а також оновлення стану інтерфейсу.
 
Рисунок 2.3 – UML-діаграма пакетів мобільного застосунку EcoMonitor

Пакет «Мережа» відповідає за взаємодію мобільного застосунку з REST API та сервісами реального часу. У ньому реалізовані компоненти для виконання HTTP-запитів, отримання даних моніторингових станцій і роботи зі сповіщеннями через WebSocket-з’єднання.
Пакет «Моделі» містить структури даних та DTO-об’єкти, які використовуються для передачі інформації між шарами системи та обробки відповідей сервера.
Пакет «Ресурси» включає локалізаційні файли, стилі, теми оформлення, рядкові ресурси та інші елементи інтерфейсу застосунку. Завдяки цьому пакету забезпечується підтримка багатомовності та адаптація інтерфейсу під різні конфігурації користувача.
Пакет «Адаптери» використовується для організації взаємодії між окремими компонентами інтерфейсу та джерелами даних. Він забезпечує передачу й підготовку даних для відображення на екранах застосунку.
Пакет «Утиліти» містить допоміжні класи та функції, які використовуються в різних частинах системи. До них належать компоненти для форматування даних, роботи з датами, перевірки мережевого підключення та інші службові інструменти.
Залежності між пакетами демонструють напрямки використання функціональності між окремими частинами системи. Центральний пакет «Додаток» використовує компоненти мережевого шару, ViewModel, інтерфейсні екрани, моделі даних, утиліти та адаптери. Такий підхід забезпечує централізовану організацію роботи застосунку та підтримує принципи модульного проєктування.
Таким чином, UML-діаграма пакетів відображає структуру програмного коду мобільного застосунку EcoMonitor, демонструє організацію внутрішніх модулів системи та взаємозв’язки між основними пакетами проєкту.

Для демонстрації процесу взаємодії між користувачем, мобільним застосунком та серверною частиною системи була побудована UML-діаграма взаємодії. Дана діаграма відображає послідовність виконання основних дій під час роботи мобільного застосунку EcoMonitor та дозволяє проаналізувати обмін даними між компонентами системи.
На діаграмі представлений сценарій перегляду моніторингових станцій на карті. Саме цей процес є одним із ключових функціональних сценаріїв мобільного застосунку, оскільки забезпечує користувачу доступ до актуальної інформації про стан навколишнього середовища.
Процес взаємодії починається з відкриття користувачем екрана карти у мобільному застосунку. Після цього застосунок формує HTTP-запит до серверної частини системи для отримання списку доступних моніторингових станцій. Сервер обробляє отриманий запит та виконує звернення до бази даних для зчитування інформації про станції та їхні екологічні показники.

Таким чином, UML-діаграма взаємодії відображає сценарій роботи системи під час перегляду моніторингових станцій на карті та демонструє послідовність обміну даними між усіма учасниками процесу.

2.4.7 UML-діаграма діяльності (Activity Diagram)

Для опису логіки роботи системи push-сповіщень у мобільному застосунку EcoMonitor була побудована UML-діаграма діяльності. Дана діаграма демонструє послідовність виконання дій під час обробки критичних екологічних показників та відображає взаємодію між мобільним застосунком і серверною частиною системи.
На діаграмі представлений процес автоматичного формування та отримання push-сповіщення у випадку перевищення допустимого порогового значення екологічного показника датчика. Такий механізм дозволяє оперативно повідомляти користувача про потенційно небезпечні зміни стану навколишнього середовища.
Процес починається з авторизації користувача у мобільному застосунку та встановлення WebSocket-з’єднання із сервером через Socket.IO канал /notifications. Після підключення застосунок переходить у режим очікування подій реального часу.
На серверній стороні система постійно отримує показники з моніторингових станцій та виконує перевірку отриманих значень відносно встановлених порогів. Якщо значення не перевищує допустимий рівень, сервер продовжує моніторинг без формування додаткових подій.
У випадку виявлення критичного перевищення сервер формує спеціальну подію threshold_alert та передає її мобільному застосунку через Socket.IO-з’єднання. Отримавши повідомлення, застосунок виконує обробку JSON-даних та перевіряє коректність отриманої інформації.
 
Рисунок 2.5 – UML-діаграма діяльності мобільного застосунку EcoMonitor

Якщо дані є валідними, мобільний застосунок оновлює інформацію на карті та змінює маркер відповідної станції для візуального позначення небезпечної ситуації. Додатково перевіряється наявність дозволу на системні push-сповіщення.
У разі наявності дозволу користувачу відображається системне push-сповіщення Android. Незалежно від цього у застосунку відкривається діалогове вікно ThresholdAlertDialog, яке містить інформацію про критичне перевищення показників.
Користувач може перейти до перегляду проблемної станції на карті або закрити діалогове вікно. У випадку вибору перегляду застосунок автоматично фокусується на відповідній станції моніторингу.
Таким чином, UML-діаграма діяльності демонструє логіку роботи системи сповіщень EcoMonitor, послідовність обробки критичних подій та механізм взаємодії між серверною частиною і мобільним застосунком у режимі реального часу.

2.4.8 Socket пiдключення до backend-застосунку

Для забезпечення роботи системи сповіщень у режимі реального часу в мобільному застосунку EcoMonitor було реалізовано Socket.IO-підключення до серверної частини системи. Використання WebSocket-технології дозволяє отримувати повідомлення про критичні екологічні події без необхідності постійного надсилання HTTP-запитів до сервера.
Socket-з’єднання реалізоване у вигляді окремого клієнтського компонента EcoMonitorSocketClient, який відповідає за встановлення, підтримку та обробку WebSocket-підключення між мобільним застосунком і backend-сервером.
Під час ініціалізації клієнта передаються:
-базова адреса серверної частини;
-callback-функція для обробки критичних сповіщень;
-callback-функція для відстеження стану з’єднання.
Для обробки JSON-даних використовується бібліотека Gson, яка забезпечує автоматичне перетворення отриманих повідомлень у Kotlin-об’єкти типу ThresholdAlertPayload.
Метод connect() виконує підключення до Socket.IO-сервера. Перед встановленням нового з’єднання виконується перевірка поточного стану socket-клієнта для уникнення повторного підключення.
У конфігурації Socket.IO використовуються такі параметри:
-автоматичне перепідключення;
-необмежена кількість спроб повторного підключення;
-затримка між спробами перепідключення;
-підтримка транспортів websocket та polling.
Підключення виконується до namespace /notifications, який використовується серверною частиною для передачі push-подій у режимі реального часу.
Після успішного встановлення з’єднання клієнт підписується на стандартні Socket.IO-події:
-EVENT_CONNECT;
-EVENT_DISCONNECT;
-EVENT_CONNECT_ERROR.
У випадку успішного підключення застосунок отримує повідомлення про зміну стану з’єднання та оновлює відповідний індикатор у системі. При втраті з’єднання або виникненні помилки виконується обробка помилки та автоматичне перепідключення.
Основною подією системи є threshold_alert, яка використовується для передачі інформації про критичне перевищення екологічних показників. Після отримання цієї події мобільний застосунок виконує:
-зчитування JSON-об’єкта;
-десеріалізацію даних;
-перевірку коректності отриманого повідомлення;
-передачу обробленого payload до системи сповіщень застосунку.
У випадку помилки десеріалізації або пошкодження даних застосунок виконує логування помилки без аварійного завершення роботи системи.
Для завершення роботи socket-з’єднання використовується метод disconnect(), який:
-розриває WebSocket-підключення;
-видаляє всі підписки на події;
-очищає socket-об’єкт;
-оновлює стан підключення у застосунку.
Наявність окремого Socket.IO-клієнта дозволяє ізолювати логіку роботи з WebSocket-з’єднанням від інших компонентів мобільного застосунку, що покращує модульність системи та спрощує подальшу підтримку програмного коду.
Таким чином, реалізований механізм Socket.IO-з’єднання забезпечує стабільну взаємодію мобільного застосунку EcoMonitor із backend-сервером та дозволяє оперативно отримувати сповіщення про критичні зміни екологічних показників у режимі реального часу.
Повний код Websocket client наведений в додатку А.

2.4.9 Локалізація мобільного застосунку

Для забезпечення підтримки багатомовності в мобільному застосунку EcoMonitor було реалізовано власний механізм локалізації інтерфейсу користувача. Система локалізації дозволяє динамічно змінювати мову застосунку без необхідності перезапуску програми та забезпечує підтримку української й англійської мов.
Основою системи локалізації є об’єкт AppLanguage, який містить константи доступних мов та реалізує механізм нормалізації мовних кодів. У застосунку використовуються мовні коди en та uk, а мовою за замовчуванням визначена англійська.
Метод normalize() використовується для перевірки та уніфікації отриманого мовного коду. Це дозволяє коректно обробляти різні варіанти позначення української мови, зокрема ua та uk. У випадку отримання невідомого значення система автоматично використовує англійську локалізацію.
Для перетворення мовного коду у відповідний об’єкт Locale використовується метод toLocale(). Завдяки цьому забезпечується інтеграція системи локалізації з Android Configuration API.
Збереження вибраної мови реалізовано через клас LocalePreferences, який використовує SharedPreferences для локального зберігання налаштувань користувача. Даний компонент дозволяє:
-отримувати поточну мову застосунку;
-змінювати мову інтерфейсу;
-автоматично зберігати вибрані параметри між сесіями роботи застосунку.
Для динамічного застосування локалізації використовується composable-компонент ProvideAppLocale. Даний компонент створює локалізований ConfigurationContext та передає його через CompositionLocalProvider усім дочірнім composable-елементам інтерфейсу.
Під час зміни мови формується нова конфігурація Android із відповідним об’єктом Locale. Після цього застосунок створює локалізований контекст, який використовується для отримання ресурсів відповідною мовою.
Окремий composable-компонент LocalizedContent використовується як глобальна точка підключення системи локалізації до інтерфейсу застосунку. Він автоматично отримує поточну мову з SharedPreferences та передає її у ProvideAppLocale.
Для отримання локалізованих рядків реалізована функція localizedStringResource(), яка є аналогом стандартного stringResource(), але працює з локалізованим контекстом застосунку. Дана функція дозволяє:
-отримувати рядкові ресурси відповідно до вибраної мови;
-підтримувати форматовані рядки;
-автоматично оновлювати текст інтерфейсу після зміни локалізації.
Під час формування локалізованого контексту додатково враховуються особливості Android API різних версій. Для Android Nougat та новіших версій використовується LocaleList, що забезпечує коректну роботу багатомовної конфігурації системи.
Реалізований механізм локалізації дозволяє централізовано керувати мовними налаштуваннями застосунку, забезпечує підтримку багатомовності та покращує зручність використання.

2.5 Висновок

У ході виконання лабораторної роботи було розроблено мобільний застосунок EcoMonitor для платформи Android з використанням мови програмування Kotlin.
Було реалізовано взаємодію застосунку із серверною частиною системи через REST API, створено архітектуру застосунку на основі MVVM та забезпечено можливість перегляду екологічних показників у режимі реального часу.
Також були побудовані UML-діаграми, що описують структуру та поведінку системи.
